# Handoff для OpenCode: «ПрорАКТ 360» → полноценный пилот

## Цель

Довести текущую ветку до рабочего Telegram-пилота для Виталия. Мастер должен
вести реальные объекты, сметы, акты, оплаты и фото скрытых работ. Заказчик,
привязанный по Telegram user ID, должен видеть только свой объект в отдельном
кабинете: прогресс, этапы, скрытые работы, фото, финансы и документы.

## Репозиторий и ветка

- Репозиторий: `Sereban-glitch/proakt-build-bot`
- Рабочая ветка: `design/miniapp-command-center`
- Pull request: `#1`
- Не начинать интерфейс заново: продолжить существующую архитектуру и дизайн.

## Что уже готово

- Переработанная админская Mini App с четырьмя основными разделами.
- Новый бренд `ПрорАКТ 360`, тёмная тема и Telegram-аватар.
- Отдельный мобильный кабинет заказчика с четырьмя экранами:
  `Обзор`, `Ход работ`, `Финансы`, `Документы`.
- Карточка доступа заказчика в объекте админки.
- Демонстрационная база, откалиброванная по обезличенным материалам Виталия.
- Сгенерированный визуальный отчёт скрытых работ «до → грунтование → после».
- Существующий Go-бэкенд, PostgreSQL-схема, Telegram initData-проверка, CRUD
  объектов/актов/оплат/смет/прайса, фото, XLSX, публичные ссылки на сметы.

## Главный разрыв между демо и пилотом

Сейчас откалиброванные данные живут в `mock.js`, а кабинет заказчика содержит
статическую разметку. При настоящем запуске из Telegram админка переключается
на `/api/*`, поэтому данные нужно перенести в PostgreSQL и подключить кабинет
заказчика к API. Простого размещения статических файлов недостаточно.

## Обязательные задачи пилота

1. Сделать повторяемый seed/import откалиброванной базы из `mock.js` в
   PostgreSQL для Telegram chat ID Виталия. Seed не должен дублировать строки
   при повторном запуске.
2. После импорта Виталий должен уметь удалить ненужные демонстрационные строки,
   добавить реальные и полностью редактировать объект через существующую
   админку.
3. Добавить модель доступа заказчика: минимум `object_id + telegram_user_id +
   status + created_at`; один заказчик видит только разрешённые объекты.
4. Сделать серверные клиентские endpoints только для чтения: обзор объекта,
   прогресс, этапы/скрытые работы, фото, акты/оплаты и документы. Проверять
   Telegram initData и право доступа на каждом endpoint.
5. Перевести `client.html` с захардкоженных значений на эти endpoints, сохранив
   текущий дизайн, названия четырёх вкладок и строительный фотоотчёт.
6. В админке заменить маску `583•••741` настоящей формой привязки Telegram ID,
   отключением доступа и кнопкой «Открыть как заказчик».
7. Хранить загруженные фото в устойчивом `FILES_DIR`/object storage. Не терять
   их при перезапуске или деплое.
8. Подготовить production-конфигурацию: `BOT_TOKEN`, `DB_DSN`, `FILES_DIR`,
   `WEBAPP_LISTEN`, `WEBAPP_URL`, HTTPS reverse proxy, резервные копии БД и
   каталога фото.
9. Настроить BotFather по `docs/brand/BOTFATHER.md`; загрузить PNG-аватар и
   указать HTTPS Mini App URL.
10. Проверить разграничение ролей двумя Telegram-аккаунтами: Виталий видит
    админку и все свои объекты, заказчик — только назначенный объект и только
    разрешённые финансовые данные.

## Критерии готовности

- Бот открывается по `/start`, кнопка `🧰 ПрорАКТ 360` запускает Mini App.
- После перезапуска сервера все изменения и фотографии сохраняются.
- Начальные суммы совпадают с контрольными значениями выше.
- Виталий может редактировать/удалять импортированные данные без правки кода.
- Заказчик не может подобрать чужой `object_id` или получить админские API.
- Фото скрытых работ отображается и в админке, и в клиентском кабинете.
- Экспорт XLSX и существующий сценарий публичной сметы не сломаны.
- `go test ./...` и фронтенд-проверки проходят перед деплоем.

## Необходимые секреты и инфраструктура

Не коммитить секреты. Для развёртывания получить у владельца:

- токен нового/существующего бота от BotFather;
- домен или HTTPS URL;
- доступ к Linux-серверу либо выбранной PaaS;
- PostgreSQL DSN;
- Telegram user ID Виталия и тестового заказчика.

Если инфраструктуры ещё нет, сначала поднять отдельный staging-пилот, а не
менять потенциально работающего бота без возможности отката.
